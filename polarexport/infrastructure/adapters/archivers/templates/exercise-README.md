# $TOOL_NAME exercise export

Generated by **$TOOL_NAME** v$TOOL_VERSION on $GENERATED_AT.

This archive holds exercise sessions pulled from the Polar AccessLink `/v3/exercises` endpoint and
accumulated in a local store over time — it was **not** produced by a single API call, so sessions
inside it may have been captured weeks apart. It is meant to be attached to a prompt so an AI agent
can analyse training load and effort without consulting Polar's own API documentation.

Requested range: **$DATE_MIN → $DATE_MAX** ($EXERCISE_COUNT sessions, $TOTAL_DURATION_SECONDS s total
duration, $TOTAL_CALORIES kcal total).

## Availability

`$AVAILABILITY`

`available` — exercise data was requested and at least one session was found in the local store.
`unavailable` — Polar denied access to the exercises source (missing user consent). `no_data` — the
source was requested, consent was fine, but the local store held nothing for it in this range.

## The 30-day retention window

Polar AccessLink v3's `/v3/exercises` endpoint retains only the last **30 days** of sessions — not
the 28 days sleep, nightly-recharge and SleepWise data are bound by (see the night export's README).

## `exercises.json`

A single JSON envelope holding one entry per session, sorted ascending by `start_time`. Every key is
present even when its value is `null` — an absent key and a `null` key read differently to a
consumer. The one exception is `heart_rate_per_minute`, covered below.

| Field | Unit | Meaning |
|---|---|---|
| `id` | string | Polar's session id |
| `start_time` | ISO-8601 datetime, local offset | When the session started. Do not normalise to UTC — the local offset is meaningful training context |
| `date` | `YYYY-MM-DD` | The local calendar date `start_time` falls on |
| `sport` | label | Polar's own token — **not** the account's raw top-level `sport` field, which is frequently the useless `"OTHER"`. See "`sport` vs `sport_label`" below |
| `sport_label` | string | Human-readable form of `sport`, e.g. `"Kickboxing Martial Arts"` from `KICKBOXING_MARTIAL_ARTS` |
| `duration_seconds` | seconds | Session duration. Polar's API returns this as an ISO-8601 duration; converted here |
| `calories` | kilocalories | Polar's own total |
| `calories_per_hour` | kcal/h | **Derived**: `calories / (duration_seconds / 3600)` |
| `distance_km` | kilometres | Polar's API returns metres; converted here. `null` for sessions with no GPS/distance data (e.g. indoor kickboxing) |
| `average_speed_kmh` | km/h | **Derived**: `distance_km / (duration_seconds / 3600)`. `null` whenever `distance_km` is `null` |
| `speed.average_kmh` | km/h | Mean of Polar's per-second speed sample series, including zero samples. Close to `average_speed_kmh`; a large gap means the series has gaps |
| `speed.maximum_kmh` | km/h | Fastest recorded sample |
| `speed.minimum_kmh` | km/h | Slowest **moving** sample — zero samples are excluded as pauses, so this is never `0` |
| `heart_rate.average` / `.maximum` | bpm | Polar's own figures |
| `heart_rate.minimum` | bpm | **Derived** — Polar's `HeartRate` schema has no `minimum`; this is computed from the per-second sample series, which is never itself shipped in this archive |
| `heart_rate_zones` | see below | Time spent in each of the user's five heart-rate zones |
| `heart_rate_per_minute` | bpm, one value per minute | See "`heart_rate_per_minute`" below — present only when this archive was built with samples included |
| `training_load` | see below | See "Training load" below |
| `device` | string | The device or app that recorded the session |
| `running_index` | integer | Polar's running performance index, when the device supports it |
| `fat_percentage` | percent | Estimated share of calories burned from fat, when Polar reports it |

### `speed` vs `average_speed_kmh`

`average_speed_kmh` is **derived** from `distance_km / (duration_seconds / 3600)` — the whole-session
average, including any time spent stopped. The `speed` block instead comes from Polar's per-second
speed sample series, so `speed.average_kmh` measures the same thing but including every sample the
device recorded, stopped or moving. Comparing the two shows how much of a session was spent
stationary: a large gap between them means the session had significant stopped time. `speed` is
`null` for every indoor session — Polar's device does not record a speed series without GPS — and the
km/h units were verified against a session with an independently known distance and duration, not
assumed from the API schema.

### `sport` vs `sport_label`

Polar's raw payload carries two sport fields: a top-level `sport`, which on this user's devices is
almost always the useless `"OTHER"`, and `detailed_sport_info`, which actually names the activity
(e.g. `"KICKBOXING_MARTIAL_ARTS"`). This export's `sport` field is `detailed_sport_info` — the token
that is actually useful — falling back to Polar's raw `sport` only when `detailed_sport_info` is
absent. `sport_label` is the same value, title-cased for readability.

### Heart-rate zones

`heart_rate_zones` is a list of up to five entries:

| Field | Unit | Meaning |
|---|---|---|
| `index` | 0–4 | Zone number, lowest intensity first |
| `lower_limit` / `upper_limit` | bpm | The zone's heart-rate boundaries |
| `seconds` | seconds | Time spent with heart rate inside this zone during the session |

The boundaries are **this user's own Polar zone settings**, not a population standard — time spent
in Z3 is a personal intensity statement, not an absolute one comparable across users.

### `heart_rate_per_minute`

$SAMPLES_NOTE

When present, it is one averaged bpm value per minute of the session, starting at `start_time` —
minute-resolution, not second-resolution. The underlying per-second sample series lives in
`data/raw/` locally but is deliberately never shipped in this archive.

### Training load

| Field | Unit | Meaning |
|---|---|---|
| `cardio_load` | float | Polar's cardiovascular training load estimate for this session |
| `cardio_load_interpretation` | label | Polar's verbal reading of `cardio_load` — see the scale below |
| `muscle_load` | float | Polar's muscular training load estimate, when the device measures it |
| `muscle_load_interpretation` | label | Verbal reading of `muscle_load` |
| `perceived_load` | float | Training load derived from a self-reported RPE, when one was logged |
| `perceived_load_interpretation` | label | Verbal reading of `perceived_load` |

`muscle_load` and `perceived_load` are `null` on devices that do not measure them, which for this
user's watches is all of them — `null` here does not mean "no training load", only "not measured".

## Profile

$PROFILE_NOTE

`manifest.json`'s `profile` block carries the same figures for machine consumption. They exist to
normalise intensity: an agent computing "% of estimated max heart rate" needs age (from `birthdate`)
and can cross-check `calories_per_hour` against body weight. **`estimated_max_heart_rate` is
`220 - age`** — a population formula with roughly ±10 bpm of spread, not this user's measured
maximum. Any "% of max" computed from it inherits that error and should be presented as an estimate.

## `null` vs `0`

`null` means the device or Polar did not report that field for the session — it is not the same as a
measured value of `0`. Do not treat a `null` field as zero in any analysis.

## `raw/`

When this archive was built with raw payloads included, `raw/exercise/<date>-<id>.json` holds the
untouched Polar API response for that session, exactly as AccessLink returned it — including the
per-second sample series that `exercises.json` deliberately leaves out.

## `manifest.json`

A machine-readable summary of this export: tool version, requested date range, availability, session
and calorie totals, a per-sport breakdown, and the profile block. It repeats information already in
this README in a form meant for automated consumers rather than for a human or AI reading the
archive directly.
